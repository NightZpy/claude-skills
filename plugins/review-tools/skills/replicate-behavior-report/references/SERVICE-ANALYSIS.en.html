behavior-report-kit · decision analysis

Turning the kit into an MCP service: is it worth it?

July 6, 2026 · analysis + full proposal · market research verified the same day

PROPOSAL — nothing built current kit: still operational LLM layer: deferred to the end
Executive verdict

The market gap is real and verified: today no product combines evidence review for a non-technical owner with a verdict the coding agent reads back. And no one — literally no product found — treats files, database rows, emails, or payloads as first-class reviewable evidence.

But that doesn't mean "build it now." As currently framed, the service is only worth it if the intent is a multi-team product. For 1–3 of your own repos with one agent at a time, the current kit wins on total cost: zero infrastructure, zero operations, and per-run token spend barely changes with the service. The exception isn't about the number of repos but the number of agents: a single large repo where several engineers work on features in parallel with several AI agents already justifies the service — the kit isn't built for that concurrency (colliding baselines, accepts overwriting each other, scattered reports), and it is, in fact, the ideal pilot for phase 0. The recommendation is a three-rung ladder: ① port to the kit what doesn't need a server (background evidence), ② a cheap validation phase 0 (minimal, single-tenant, no-billing service) that tests the verdict loop on your own repos, and ③ decide on the SaaS only with that signal in hand — because the window exists but is closing: Ranger has already closed the human→agent loop in its developer version.

What it is, in one picture

Today the kit gets replicated: each repo installs and adapts ~2,000 lines of generator, ffmpeg encoding, and doctrine. The service inverts that: the agent — Claude or any LLM — only captures evidence and sends it; the service generates, hosts, and returns the owner's verdict via MCP.

Client — the user's machine

  • The app under test on any platform — web, mobile (Android/iOS emulator/simulator), desktop, daemon — + deterministic fixtures
  • features.json versioned in git — the source of the "what"
  • E2E stories that run against the local app
  • Evidence capture: paced actions, decode/paint gates, raw video; for background: the row, the file, the .eml, captured in the moment
  • Local metrics (coverage, mutation) — the code never leaves
  • Thin client: local MCP that packages manifest + paths and uploads

Service — once, for everyone

  • Ingest + evidence contract validation
  • Media encoding (H.264/GIF ladders) — ffmpeg disappears from the client
  • Report generation + hosting with per-project auth
  • Owner's verdict persisted, readable by the agent via MCP
  • Content-hash baselines, history, metrics ratchet
  • LLM layer — deferred, final phase
client ── manifest + media ──▶ service ── review URL ──▶ owner ── verdict ──▶ agent (MCP)

The real economics: where you save and where you don't

The question was "do we spend fewer tokens?" The honest answer has three parts, and the first is a no:

  • Per run: practically the same. What consumes agent work on each run — writing stories, debugging failures, capturing — stays on the agent's side in both models. The local generator is already deterministic node: it runs for free.
  • Per install: large savings. Replicating the kit in a new repo is an agent job worth hundreds of thousands of tokens (adapting the generator to the stack, verifying with Playwright, iterating). With the service: an API key + writing stories.
  • Per maintenance: the compounded savings. Today every kit improvement gets re-synced repo by repo — tokens × N repos, every time (this repo and its audits exist because of that problem). With the service, it's updated once and every project receives it at zero cost.

Against that, two new costs the kit doesn't have: building it (it's an entire product: API, storage, encoding, frontend, MCP, auth — weeks of agent work, meaning a lot of tokens today) and running it (hosting, media storage, domains, backups: tens of dollars a month that grow with usage, plus maintaining something that can go down on a Sunday).

ScenarioInstallsThe current kitThe serviceVerdict

C · SaaS product for third parties N open-ended Doesn't scale: no one replicates 2,000 lines just to try you out Only viable path; the market gap is real YES, WITH CONDITIONS

The token figures are field estimates (the install in the reference repo cost roughly that much), not exact measurements. The structural point doesn't depend on the figure: the savings are in install and maintenance, never in the run.

Scenario B′ deserves emphasis because its argument isn't tokens: it's capability the kit doesn't have. The kit assumes one agent and a linear flow — one review-state.json, one history, one report. With several engineers and several AI agents working on features in parallel on the same repo, that breaks down on its own: the versioned baselines collide on every merge, one branch's --accept overwrites another's, and the owner ends up with one artifact link per agent, with no overview and no review order. The service turns that concurrency into its natural use case: every run arrives tagged by feature/branch/agent, the owner sees one queue ("5 stories from 3 features await your review"), and each verdict comes back via MCP to exactly the agent waiting for it. It's also the perfect pilot for phase 0: it demands multi-agent coordination but not public multi-tenancy, billing, or onboarding strangers.

Willingness-to-pay signal from the neighboring market: Chromatic charges $179–399/mo, Currents $49/mo, gotoHuman $99–950/mo, and a managed human gate like Bug0 reaches $2,500/mo. Real budget exists in this category — for scenario C, not for A.

The window is closing along the wrong axis of copying: the transport (verdict→agent via MCP) is the easy part to replicate, and Ranger already has it in its dev version; Momentic, Shiplight, and Currents already publish MCP servers. A pivot by any of them toward the "product owner" persona is incremental. The defensible moat is the combination (a)+(b): owner-language stories + background evidence + baseline semantics — not the MCP.
4

What's missing for it to be worth it

As we'd been framing it so far — "the generator, but remote" — it's not worth it: that's a render service, pure commodity. What turns it into something that holds up is this, in order:

  1. The complete verdict loop, with a channel to the human. get_verdict isn't enough: the owner needs to find out there's something to review (push/email: "12 stories await your review") and the agent needs to be able to wait for the verdict (wait_for_verdict with a timeout) to keep going on its own. Without notification there's no loop; there's just a URL someone forgets to open.
  2. Accept from the UI with write-back to the repo. If the owner already marks GOOD story by story, forcing "the agent runs --accept afterward" is inherited friction. The accept happens where the review happens; the service returns the updated baseline and the thin client commits it to the repo — git remains the auditable record.
  3. Background evidence with primary material, from day one of the contract. It's the differentiator no one has (verified). If the service is born "UI-only" it's a poor man's Chromatic; if it's born with downloadable timeline/state-diff/artifact, it's born without competition.
  4. Onboarding without the kit: 20 minutes, any agent. If installing the client still costs hundreds of thousands of tokens, the service never takes off. The goal: MCP config + a short capture prompt ("this is how you produce valid evidence") and the first report ships the same afternoon. The REPLICATION-PROMPT shrinks down to an ingest contract.
  5. Semantic history + content-hash dedup. Version runs (data), not HTML: "when did this story turn green?" becomes answerable, identical media gets stored once, and every UI improvement re-renders the whole history retroactively.
  6. CI as an emitter. The run can come from the pipeline, not just from the agent on the laptop — without this, it doesn't get into teams.
  7. Multi-project dashboard. An owner with N products reviews everything in one place; it only makes sense once the service exists, so it's a structural advantage.

And what not to do: don't compete on pixel-diff (a saturated commodity), don't try to centralize capture (impossible: the app lives on the client's machine), and the LLM layer stays for last — the loop has to prove value with humans before optimizing what the human sees.

API and MCP surface proposal

The MCP runs locally (stdio): the agent passes it paths; the local server reads the files and uploads them over HTTP. Not a single video byte crosses the model's context. Media is content-addressed: before uploading, the client asks which hashes are missing and only uploads what's new.

MCP tool (agent)Underlying RESTWhat it does
submit_runPOST /v1/projects/:id/runs
PUT /v1/blobs/:hash		Sends the manifest (spec + results + evidence with paths); the local server uploads only the blobs whose hash doesn't already exist. Returns run_id + review URL.
get_runGET /v1/runs/:idStatus: processing / ready / verdict in. Includes the NEW/CHANGED summary vs. baseline.
wait_for_verdictGET /v1/runs/:id/verdict
(long-poll) · optional webhook		Blocks until the owner finishes (or timeout). Returns the verdict per story: GOOD / FAIL / NOTES(text) / UNMARKED.
accept · accept_onlyPOST /v1/runs/:id/acceptSame semantics as the kit (scoped, content-hash). Returns the updated baseline to commit to the repo.
get_historyGET /v1/projects/:id/historyMetric rows + accepted runs; the ratchet validates server-side and reports what would trigger a regression.

The manifest — the natural extension of the kit's current contract (same features.json, same badges, same accept semantics):

  "spec": { …features.json in full… },
  "run": { "startedAt": "…", "suite": "e2e", "metrics": { "coverage": 84.1, "mutation": null } },
  "stories": [{
    "id": "checkout/confirmacion-email",
    "status": "pass",
    "evidence": [
      { "type": "video",      "blob": "sha256:9f31…", "caption": "The order is submitted and the confirmation appears" },
      { "type": "timeline",   "events": [
          { "t": "10:02:01.120", "e": "POST /orders accepted" },
          { "t": "10:02:03.480", "e": "worker processed the order" },
          { "t": "10:02:04.010", "e": "confirmation email sent" } ] },
      { "type": "artifact",   "blob": "sha256:c04a…", "kind": "eml",
        "caption": "The email exactly as it arrived, with the PDF attached" },
      { "type": "state-diff", "before": { "orders": 0 }, "after": { "orders": 1 },

}

Each piece of evidence: readable render + downloadable primary material. Truncation is always declared ("50 of 12,000 rows"), never silent. Auth: API key per project. The kit's entire §6 contract (badges, verdict format, accept) is preserved — the service is just another consumer of the same contract, not a new one.

A typical day for the client agent

What exactly the agent developing a product using the service does — and what it no longer has to do:

  1. agentImplements the feature in the product's repo, as always.
  2. agentDeclares the behavior in features.json: the story in the owner's language ("When the order is submitted, a confirmation email arrives with the PDF attached"), marked NEW.
  3. agentWrites the story and captures valid evidence against the app in its local environment — browser for web, emulator/simulator for Android/iOS, the window for desktop: paced actions (~400–500 ms), decode/paint gates before every screenshot, raw video; if the behavior is background, it captures the effect in the moment — the inserted row, the generated file, the .eml.
  4. agentsubmit_run with the manifest and the paths. The local MCP uploads only the new blobs (dedup by hash). It receives the review URL. No longer on its side: the 2,000-line generator, ffmpeg, HTML, CSP, artifact deploy.
  5. serviceValidates, encodes, and publishes. The owner gets the notification: "Pedidos Nube: 3 new stories await your review."
  6. ownerReviews from the phone: watches the video, opens the email exactly as it arrived, and marks story by story — GOOD, FAIL, or NOTES with text.
  7. agentwait_for_verdict wakes up with the structured verdict: 2 GOOD, 1 NOTES ("the PDF arrives without the logo"). It turns each NOTES into a fix or an issue, each FAIL into a red story that stays honestly red.
  8. agentaccept for what got approved (or the owner already accepted from the UI): it receives the updated baseline and commits it — git remains the record. The next run will show only what changed.

The agent goes from operating a pipeline to doing only what no one else can do from outside: writing faithful stories and capturing true evidence. Everything else belongs to the service.

The current report is a document you read. The service's UI is a queue you operate: the owner comes in through a notification, reviews story by story with the evidence full-screen, marks it with a thumb, and leaves knowing how much is left. The kit's already-proven mobile doctrine (no horizontal scroll at 360 px, lightbox, touch targets) is the floor, implemented just once.

Risks and open decisions

  • Market convergence (the real risk). The MCP transport is copyable within a quarter; Ranger already has it for devs. The defense is depth in what can't be copied quickly: the evidence model of owner-language + background + baselines. If it gets built, build that first.
  • Running a service is a new job. Private media from other people's apps demands serious auth, defined retention, and incident response. It's a shift in posture away from "everything lives in your repo." (The single-tenant phase 0 sidesteps this until there's a signal.)
  • Baseline: repo or service? Standing recommendation: baselines live in git (auditable, yours) and the service processes them; the accept-from-UI returns the baseline to commit (write-back), it doesn't hijack it. The verdict, though, is server-side — that's the new part of the value.
  • Privacy of the primary material. Real rows and files can carry sensitive data → the deterministic-fixtures doctrine holds, plus configurable redaction per project. The LLM layer (whenever it arrives) is opt-in per project.
  • Longevity. If the service dies, the self-contained export and the replicable kit keep working — that emergency exit is kept on purpose, and it's also the sales argument against lock-in.
9

Roadmap: validate cheap before building expensive

PHASE 0 · validation

Minimal single-tenant service, no billing, no multi-tenant auth: ingest + generation (reusing the kit's generator almost as-is) + simple hosting + persisted verdict + 4 MCP tools (submit_run, get_run, wait_for_verdict, accept) + email notification. Use it on 2–3 real repos of your own. Measurable success criterion: the complete loop —run → notification → mobile review → verdict → the agent acts— happens with no copy/paste, and the owner prefers it to the current artifact. If they don't, it was a cheap lesson.

PHASE 1 · core

Only with signal from phase 0: multi-project, API keys, content-addressed dedup, semantic history, full server-side encoding, CI as emitter. Full parity with the kit for UI evidence.

PHASE 2 · background

The non-UI evidence vocabulary with primary material (timeline, state-diff, artifact) — the differentiator with no competition. Independent of this: porting the vocabulary to the current kit is worth it even if the service doesn't move forward.

PHASE 3 · review

The review queue matures: multi-project dashboard, accept-from-UI with write-back, push notifications.

PHASE 4 · LLM

The service's LLM layer (evidence QA, editorial, triage) — saved for last by explicit decision on 2026-07-06, opt-in, and it never issues the verdict.

Today's decision isn't "build the SaaS": it's "spend a phase 0." It's the small bet that buys the information — if the verdict loop changes how you review your own products, the rest of the analysis kicks in; if not, the current kit was already the right answer.
